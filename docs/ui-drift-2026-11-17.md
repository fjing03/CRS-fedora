**B2 — WITHDRAWN 2026-11-17, same day. It was a flaw in my method, not in the page.**

The finding was "Hover a colour to learn more prints on a touch phone". It does not:
`ui-legend-bar.blade.php` already carries both strings, and `theme.css:2253/2261-2262` swaps
them under `(hover: none)`. Measured with a real touch context
(`hasTouch`, `isMobile`, mobile UA, 390 wide): `hoverSpan: none, touchSpan: inline`,
`matchMedia('(hover: hover)').matches === false` → the page says **"Tap a colour to learn
more"**. With a mouse at 390 it says "Hover", which is correct.

**The method consequence, which matters for pass 2:** a 390-wide capture with a mouse is not
a phone. Every state that depends on pointer capability — hover copy, 48 × 48 touch targets,
`:hover` styling — must be captured with `hasTouch: true, isMobile: true` or it will report
the desktop behaviour at phone width. Pass 1 captured the phone band with a mouse, so **every
finding whose litmus is "on a phone" needs re-checking under touch**. B1 is unaffected: it is
a structural difference visible in either mode.

The fingerprint pass compared 189 shared classes between live and drawing at 1440 and 390, on

lessons worth keeping:

- **Most "differences" were structure, not styling.** `.cell-code` and `.rc-code` differ in

  keep reporting live improvements as drift.

### 7.2 `DESIGN.md` against `theme.css`

Checked every claim the document makes about the shipped stylesheet.

**Accurate:** the badge (22 px, `3px 10px`, 12/600, outline inside the box); the radius ladder
4/8/10/12/14/16/999; the three z-index families 1200/1400/9999; three shadow steps, each with an
offset; the pop-up's 680 px ceiling and 420 px floor above a 601 px viewport; ownership at
**3 px / 0.5 px**; the paper palette as fixed light `--p-*`; the print day strip at 78 px; the
absence of any `--spacing-*` token (0 matches — the document says so rather than inventing one);
the chip's 26 px "×"; the 56 px top bar.

**One mismatch, and it was a colour, not a typo. Fixed the same evening (`dc60093`).** The
document said *"secondary exists in the palette and is reserved, not used for status"*, and the
stylesheet used it for exactly one status word:

```css
.summary-points .summary-normal { color: var(--color-on-secondary-container); }
```

Crimson (`#E8668A` dark, `#7A0033` light), so the week summary's legend printed the word
**"Normal"** in crimson while normal classes were green on every timetable. It arrived with the
flip-card summary work (`0851531`, 2026-11-14) and reads like the last palette slot being used so
each keyword had a colour — not a decision anyone argued for. Its three siblings already used
`on-*-container` tokens; it now uses the success one and computes to `#1B5E3A` in the live panel.

Confirmed the way a reader would want it confirmed: the served CSS was re-fetched with the cache
off, so this is the file the browser actually got, not the one on disk.

### 7.4 Was the crimson "Normal" a one-off? Yes

The bug had a shape worth searching for: *a status word wearing a colour that means something
else*. Checked twice, read-only.

**In the stylesheet:** 53 declarations set a text colour on a selector that names a status word
(normal, available, approved, replacement, pending, conflict, holiday, rejected, overdue,
cancelled). 50 match their meaning. The three that did not were checked by hand and cleared: the
`+` glyph on an available cell sits on a blue action button, the holiday empty state inherits red
from its parent, and the hovered holiday badge takes the inverse colour on purpose.

**On the live pages:** 22 distinct status words rendered across My Timetable, Cohort, Venue, My
Replacements, Request Approval and Replacement History, compared against their expected colour
family. After discarding white-on-coloured-fill badges, grey summary *labels* (a category name is
not a status) and table headers, **no second instance**.

One deliberate difference surfaced, recorded so nobody "fixes" it: **the print key** renders
"Normal", "Replacement" and "Pending" as neutral text beside coloured swatches. On paper the
swatch carries the colour, so the word does not need to.

### 7.5 The grid's 586px, ruled and answered

The finding in §6 (I7) was that the arrangement grid runs 586px past its card at 1440. The user
looked at it and said they saw no problem — and after re-measuring, the disagreement turned out to
be about *what kind* of problem it is.

Measured at 1440: table **1976px** in a **1390px** card, `overflow-x: scroll`, the last visible
column clipped mid-label (`15:00 / 16:00`), and **`scrollbarH: 0`** — Chromium's overlay scrollbars
take no space, so nothing on screen said the week continued. At 1100 the hidden strip is 926px.

But 08:00–15:00 and all seven days *are* visible, and this dataset has almost nothing after 16:00.
So it is not a layout defect; it is a **discoverability** one. The user ruled: **keep the density,
make the hidden part obvious** — not the cell-squeeze first proposed here.

Done in the shared grid partial: a chevron pill plus a 40px edge fade at the side that has
something hidden, flipping edge after a scroll and vanishing at the end; `aria-hidden`,
`pointer-events: none`, hidden in print. No cell resized, no column removed.
Receipt: `tests/grid-scroll-cue.spec.ts` 4/4.

Worth carrying forward: the read-only timetables hide the same 586px at 1440, so they get the cue
from the same partial at no extra cost. **Request Approval does not** — it builds its own
`.grid-scroll` markup instead of the partial, so any overflow there is still silent.
