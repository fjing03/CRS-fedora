# Design: span-aware-approval-flow

**Reads against frozen `proposal.md` (Batch 1, 3 reviewer rounds).** The explore-brief's
decisions table (Q1–Q12 + tracked Q13) is binding. Naming/SSOT approach: everything rides the
`replacement_request_slots` junction + `time_slots.version` state machine that
`full-block-reservation` landed; NO new migration, NO new conflict token names.
**Alias note (RR1/R5 🔴, declarative):** the frozen PROPOSAL's "D7 original-release" ≡ THIS design's **D3**; this design's "D7" = the RequestApproval page internals. Never conflate.

## Design skeleton

```
RequestApproval (Livewire, route already gated auth+pl)
   render(): pendingRows() + decidedRows() + summaryCards + filters (localStorage parity frozen template)
        │  approvalsGuidance: ONE shared validity predicate (S1) per row
        ▼  wire actions: approve(id) / reject(id, reason) / bulkApprove() / bulkReject(reason) / cancelRequests parity
ApproveRequest (D1) & RejectRequest (D2)
   DB::transaction: lock request → ordered lock junction slots → check ALL → flip ALL version-checked
   → decision stamps + audits → D7 release (approve) / junction DELETE (reject) → queue mails
mail: ReplacementSubmitted / ReplacementDecided / cohort leg  (ShouldQueue, log mailer, Q7=A)
```

## Key flows (who calls who, params)

- `RequestApproval::render()` → D6::evaluate per pending row (badge) → D5::toRow per row (shape)
  → blade renders the FROZEN markup with the real rows.
- `approve(requestId)` → D1 → payload `{ok|conflict_reason}` (existing modal contract) —
  success re-renders the queue (row leaves pending) + summary cards recalc server-side.
- `reject(requestId, reason)` → D2 (validity guard D6 shared) → same payload shape —
  `conflict_reason` = stale-rows text when release failed.
- `bulkApprove()` / `bulkReject(reason)` → D10 loop → each row's result (ok/conflict list).
- Submit side: `SubmitReplacementRequest` (+ FR 4.15 hook — D9) → mail created for `is_pl`
  recipients; queue persists (jobs table); worker drains (runbook + NFR 1.4 test).

## Page-changelog / UI-99.9%-parity notes

- The 1236-line template IS the visual authority — no new CSS, no new components; `theme.css`
 tokens only.
- The mock's OWN undo behavior (client-side `prevStatuses` restore) is NOT ported: decisions
  are final server-side. The confirm popups' "cannot be undone" copy stands verbatim.
- Summary cards + status filter + detail modal all read REAL rows (pending FCFS + decided).
  The `completed` filter option exists but its bucket is (honestly) empty — out of scope leg.
