# Proposal: full-block-reservation

**Origin:** bug-hunt **Fix 3** (user-reported span hole) + U5a canonical-span decision. Re-explored + grilled 2026-10-16 (decisions Q1–Q9, one at a time — see `explore-brief.md`; supersedes the 2026-10-13 round). **Sequencing (rehearsed, reviewer-corrected):** `arrange-intent-session-choice` is archived 2026-10-16 (the deferred "is conflicted consumer copy" item was retired inside it — OUT of scope here). `venue-page-book-affordance` (U2a)'s **feature code is live at HEAD** (tooltip/arrange/modal already in the venue blade); its SDD change dir REMAINS ACTIVE (verify/archive pending) — the merge overlap with this change is confined to the venue **read-model region** (`VenueTimetable.php:255–285` events query), which U2a's UI-affordance artifacts do not touch; U2a's blade work and this change's one-cap blade edit are disjoint regions.
**Layer:** backend write path (submit/OCC/engine/cancel/read-model) — one additive migration. No UI-page redesign; the arrangement picker gets one cap number.

## Why (the hole is live at HEAD, re-verified 2026-10-16)

A 2h replacement books and renders as a single 30-min slot; the other 3 half-hours remain legally bookable by anyone:

- `SubmitReplacementRequest::__invoke(..., int $anchorSlotId, ...)` (`app/Actions/SubmitReplacementRequest.php:33`) reserves ONLY the anchor via `$this->occ->validateAndReserve($anchorSlotId, …)` (`:76`). Reviewer-verified line-precision: orphan defence ≈`:272–277`; the "Amendment 2b" comment block `:254–260`; `CancelPendingRequest` `whereKey` ≈`:35`.
- `OCCValidator::validateAndReserve` (`app/Services/OCCValidator.php:21–67`) is a single-slot transaction: lock 1 row → status check → version-checked flip → 1 audit row.
- `CancelPendingRequest` (`app/Actions/CancelPendingRequest.php:33`) releases ONLY `replacement_time_slot_id`.
- `MatrixIntersectionEngine::validateSlot` (`app/Services/MatrixIntersectionEngine.php:172`) validates the anchor cell only.
- Schema carries a single `replacement_time_slot_id` FK (`2026_08_03_000009_create_replacement_requests_table.php:21`); the per-slot partial unique (2026_08_03_000006_*) protects individual slots.
- **New fact (2026-10-16):** the client ALREADY sends `endHour` per block (blade `proceed()` → `blocks.push({ venue, week, day, startHour, endHour })`), and `submitBlocks` (`app/Livewire/ReplacementArrangement.php:461`) IGNORES it — resolving one slot at `08:00 + startHour×30`. The span data crosses the wire today; only the server ignores it.

**🔴 The trap a naive fix walks into:** the venue page's orphan defence (`app/Livewire/VenueTimetable.php:274–279`) emits NOTHING for a `pending` slot with no active request. If span reservation flips slots 2..N to `pending` without a link back to the request, those cells fall through to the free-cell branch and — post-U2a — render as BOOKABLE `cell-available`. The fix MUST give every reserved slot a request linkage.

## In scope

1. **Junction table `replacement_request_slots`** (additive migration): `id`, `replacement_request_id` FK cascade, `time_slot_id` FK **unique**, timestamps. Unique = LIVE-reservation semantics: a slot may be junction-linked by at most one request at a time (mirrors the per-slot partial unique — nothing double-bookable).
   - **Release deletes the junction rows (`CancelPendingRequest`; future approval reuses it).** Cancel keeps the REQUEST row (`cancelled` status, decided_at — today's behavior) — cascade would fire only on DELETE, so retaining the rows would poison the released slot forever (resubmitting it re-INSERTs the same `time_slot_id` → unique violation, every booking fails identically). With release-deletes: the link exists only while the reservation lives; history stays in `audit_logs` (the per-slot release rows, Q4) + the request row itself; the venue read-model needs no filter gymnastics; and the brief's "receipt" rationale reads as "the receipt of the LIVE reservation".
   - The legacy `replacement_time_slot_id` column on `replacement_requests` STAYS (anchor identity + backward compat). Existing rows unaffected (demo DB has zero requests — verified 2026-10-16).
2. **Span source = the already-sent `endHour` (Q1): no new client field.** `submitBlocks` derives per block the raw span `endHour − startHour` (the blade's exclusive-end index makes this formula exact) and **REJECTS out-of-bounds values before any write**: `span` < 1 or > 4 or non-integer → `invalid_span` (a loser, D5-compensated) — a tampered or 3h-derived endHour NEVER silently narrows into a smaller booking. The N slots are then resolved/validated server-side (contiguity = same venue/day/week, structurally ordered start-times); the client is never trusted beyond validation.
3. **`SubmitReplacementRequest` gains `int $span = 1`** (backward compatible — every existing caller unchanged; grill Q3):
   - Resolves anchor..anchor+span−1 within the same venue/day/week via ordered `start_time` (+ `id`) lookups; missing/occupied any → `slot_not_available` **with that slot's start/end recorded into the flat-return keys** (the steady-state named-time path — see item 7); loser path unchanged: D5 compensating delete.
   - Engine pre-check over the FULL span (below).
   - Reserve **all-or-nothing in ONE transaction**: `SELECT … WHERE id IN (…) ORDER BY id FOR UPDATE` (ordered locking — no deadlock ordering trap), per-slot status check, version-checked flip `available→pending`, junction rows created, **audit row per slot flip** (grill Q4 — each carries its own `time_slot_id`; the existing per-row audit format is preserved).
   - **`span_overlap` detail (grill Q8):** on any in-span conflict the result records the FIRST failing slot's `start/end` time so the UI can say WHICH time blocked the request.
   - FOCS bound (grill Q5): **span maximum = 4 slots (2 hours)**, enforced server-side — `span` > 4 → `invalid_span` (a loser, D5-compensated); NO clamping (a user asking for 3h gets a rejection, not a silently shorter booking).
4. **Engine `validateSlot(..., int $span = 1)`** (grill Q3): validates anchor..anchor+span−1 — all slots `available`, lecturer + cohort busy vectors checked over the full span (per-slot `overlaps`), venue eligibility unchanged (one venue), day-end fit already implicit (contiguous same-day slots resolve within the grid; conforming span ≤ grid length), holiday check per slot day (same day). One rule set consumed 1× or N× — never a parallel copy.
5. **`OCCValidator` span-aware — TWO-PHASE discipline (mandated; grill Q1 review):** still ONE transaction, but **no flip ever precedes a conflict exit**: lock ALL `span` rows first (`WHERE id IN (…) ORDER BY id FOR UPDATE`), then check ALL statuses (recording the FIRST failing slot's start/end for the `span_overlap` message), and ONLY if every row passes → flip all (version-checked) + junction rows + success audit per slot. A per-slot check-flip loop is FORBIDDEN: a mid-span conflict would return `OCCResult::conflict` normally → the transaction COMMITS the already-flipped slots → D5 deletes the request → orphaned `pending` slots → the exact hole this change closes, recreated in the loser path. Request validation unchanged (pending + anchor identity). **Loser audit granularity (pinned): the two-phase conflict path emits the CURRENT single conflict audit row** (first failing slot's `time_slot_id` + reason/failed-times in `details`) — unchanged behavior — so per-slot rows are written only on success.
6. **`CancelPendingRequest` releases the span via the junction** (ordered slot release, per-slot version++ + audit; the single-slot path becomes the span=1 special case). Orphan defence keeps its safety net.
7. **`conflictText` gains `span_overlap` + its transport chain (Q8) — the named-time contract covers BOTH loser paths:** the steady-state pre-reserve slot-status check (item 3) and the OCC race window. `OCCResult` gains the failing slot's start/end; `SubmitReplacementRequest`'s return shape is **enriched** — today `['ok' => bool, 'conflict_reason' => ?string, 'request_id' => ?int]` (request_id preserved) with `failing_start`/`failing_end` keys (set by the action's span pre-check when a mid-span slot is NOT `available`, and by the OCC race conflict); `conflictText`/the client interpolate them when present, falling back to the canned `<reason>` copy otherwise. Rendered: *"Your {span}-slot ({hours}h) block runs into an existing booking at {HH:MM}–{HH:MM} — pick another slot."* Named times apply to slot-availability losers only — engine VECTOR losers (lecturer/cohort busy) keep their existing copy ("You or the cohort is no longer free…"), not a location.
8. **Read-model family — the junction's span must reach EVERY anchor-keyed consumer (round-4 scope):**
   - **Venue page (`VenueTimetable`)** — ONE event per REQUEST, not per-slot: `mergeTwinEvents` buckets by `di:start` and merges same-cell twins only — it never extends `start`/`end`, so per-slot pending events can never coalesce. The pending join keys through the junction and emits **one event per REQUEST** with `end = start + span − 1` (span from the junction row count) — the blade already renders multi-cell events via the `span-N` class + `colSpan` when `ev.end > ev.start`. The stale "exactly ONE anchor half-hour slot (spec Amendment 2b)" comment (comment block `:254–260`) becomes span-aware. AC 4 rides the one-event-per-request shape.
   - **Arrangement grid ownership read (`ReplacementArrangement::venueSlotsByWeekPayload` ≈`:326–332`)** — the pending ownership map is ANCHOR-keyed (`whereIn('replacement_time_slot_id', …)`): a 4-slot span's tail slots 2..N are junction-linked but ABSENT from the anchor column → `$proposers->get($slot->id)` is null → tails render status **4 "reserved (someone ELSE's)"** even on the OWNER's own grid (should be status 3 "mine"). Fixed: the ownership map derives from the junction (every junction-linked slot → its request's proposer); the region ENTERS the impact scope (round-4: the explore-brief's "arrangement grid — verify only" claim is WRONG under spans and is withdrawn).
   - **API read surface 1 — `myRequests()` (`app/Http/Controllers/Api/ApiReadController.php` ≈`:135–170`)** — one row per request carries only the anchor slot's 30-min time: a 2h pending displays as a half-hour booking. Fixed: the read derives the span via the junction (min/max start/end or row-per-slot) so the history list shows the true range.
   - **API read surface 2 — the venue-slots API map (same controller ≈`:685–712`)** — the cell-marking loop spans only the anchor's half-hour → tail slots 2..N are UNMARKED → API consumers render them free/bookable (the double-book hole resurfaced via API). Fixed: junction-derived span at the cell level (mark anchor..anchor+span−1), mirroring item 8's one-request shape.
9. **Arrangement picker cap = 4 (grill Q5) — every cap site enumerated, one number family:**
    - derived `BLOCK_SPAN` from `&duration=` (both boot clamps): preserves the existing `Math.max(hrs, 0.5)` lower floor and caps the top at `4` slots — a 3h handoff auto-shrinks to 2h;
    - the slot-panel resize clamp: `slotSpan` max = 4;
    - `MAX_SELECTION = max(BLOCK_SPAN, 4)` stays the existing multi-week BUDGET (total slots across weeks — a different quantity than block span; unchanged at 4) so a 1h class can still book twice (2+2) and a 2h block uses the whole budget;
    - `urlSpanLocked` keeps auto-picks at their (now ≤4) derived span.
    - **Explicitly OUT of this family:** the booking-intent banner's pinned-anchor clamp (blade ≈`:2373`, `min(max(round(pinned.duration×2),1), 8)`) — it derives the ORIGINAL class's true length for a display-only anchor slot, not the replacement selection; capping it would make the banner lie about a non-FOCS 3h original. Unchanged.
    Net: users can never select a block wider than 4 slots anywhere in the flow — no dead-end picks.
10. **Tests (grill Q7 — disposable `class_replacement_testing` only; the demo DB is never touched):** includes the DESIGNED Playwright contract change: `tests/ui-regression.spec.ts` **TC-1.4** re-pointed to the 2h cap ("of 4"; `duration=3` auto-shrinks):
    - Extend `tests/Feature/OccConcurrencyTest.php`: A reserves a 4-slot span while B targets a mid-span slot → B loses with `slot_not_available`; the winner's request owns exactly 4 junction rows; ordered-lock success path.
    - Span bounds: `span` 0, 5+ → `invalid_span` (a `conflictText` branch for `invalid_span` replaces the misleading generic fallback — bounds errors deserve a bounds message); non-integer input is asserted at its reachable surface (the JSON derivation in `submitBlocks` coerces `(int)` silently — the test pins the derived value); missing mid-slot (non-contiguous grid) → `slot_not_available`.
    - **Two-phase loser test:** mid-span occupied → the whole submit loses AND zero slots are left `pending` (anchor still `available` — the partial-flip trap is dead). The two-phase LOSER emits the existing SINGLE conflict audit row (its `time_slot_id` = the first failing slot; `details` carry the reason + failing times) — same as today's per-request conflict audit (`OCCValidator.php:69`); only the SUCCESS path writes per-slot rows.
    - Cancel: releases ALL junction slots (version++ each, audit per slot), legacy anchor-only requests keep working.
    - Engine span vectors: busy vector hitting a TAIL slot rejects the whole submit pre-reserve.
    - Read-model: a 4-slot pending request renders ONE coalesced amber span on the venue page; the arrangement grid renders the owner's span tails as status 3 "mine" (others' grids show 4 "reserved"); `myRequests()` shows the true 2h range; the venue-slots API map marks anchor..anchor+span−1 (tails not bookable via API); cancel → cells free again everywhere.
    - `span_overlap` result carries the failing slot's start/end (assertable message source).

## Acceptance criteria (verify-stage checklist)

1. A 4-slot (2h) submit locks ALL 4 slots atomically or nothing: mid-span occupied → whole submit loses, D5-compensated, with the blocking time named (steady-state pre-check AND OCC-race paths both carry it — item 7) — and **ZERO slots left `pending`** (the anchor stays `available`; test-pinned).
2. A concurrent submission targeting any slot INSIDE a held span loses politely (`slot_not_available`), never 500s.
3. Cancel frees every junction slot (version++ each, audited); the venue page AND the arrangement grid re-render the cells free (arrangement mine/other statuses correct post-cancel).
4. The venue page renders a held 4-slot pending request as ONE coalesced amber span block; `myRequests()` and the venue-slots API map show/mark the true span **while the reservation is live** (post-cancel, the anchor-only read is CORRECT — release deletes the junction rows; never re-retain them for cancelled requests).
5. `span` > 4 or malformed → rejected before any write; `validateSlot` default-1 callers byte-unchanged in behavior.
6. PHPUnit (testing DB) extended suites green; full gates green; demo DB untouched.
