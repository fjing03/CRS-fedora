## 🔍 Review Report: arrange-intent-session-choice (batch: proposal.md — round 1)

Nothing is frozen in this change yet; `explore-brief.md` is the review baseline. All five codebase "key facts" were verified against HEAD — see ✅ section.

### 🔴 Critical Issues (implementation blockers)

**[1] `tests/venue-book.spec.ts` (U2a-T3) breaks, and the proposal's test scope claims it stays green.**
Verified fact: `venue-book.spec.ts:56–66` (U2a-T3) clicks the tooltip's `#tooltipBookBtn` and asserts a **direct navigation** to `/replacement-arrangement?venue=B110&date=…&time=…&from=venue-timetable` with the intent banner. This change interposes the "Select a Session" modal: the tooltip's [Arrange] button now opens a modal (scope item 1); navigation happens only on the *modal's* [Arrange]. U2a-T3 will fail on the first run after apply. The proposal's Impact scope → Tests bullet says *"existing suites must stay green (… venue-book 6/6 …)"* and its files list contains only the two **new** specs — `venue-book.spec.ts` is nowhere in the impact inventory. An implementer following the letter of the proposal would end up either with a lying gate claim or forced into undocumented scope. Fix (proposal-level): add `tests/venue-book.spec.ts` to the test impact scope with an explicit reconciliation item (U2a-T3 becomes a two-step flow assertion; URL regressed... more precisely extended to 8 params) before freeze.

**[2] The consumer fallback has no specified mechanism to bind the occurrence it picks — first-session default can be type-incompatible (recreates the dead-end inside the new flow).**
Verified facts: `applySubjectChange` (`replacement-arrangement.blade.php:2697–2701`) sets `currentSessionId` to `window.pinnedOccurrence.sessionId` **only** when a pin exists, else the module's *first* session. Scope item 4's fallback fires precisely when **no `session` param arrived** — i.e., no pin exists. So after the fallback picks (module M, occurrence O-compatible) and (implicitly) triggers `applySubjectChange`, the bound context is O₀ = *M's first session in payload order*, which for a mixed-type module (AMCS2093 = L+P+T, the brief's own example) can have a **different type** than O. The grid's courseCtx/venue-filter then disagrees with the compatibility decision that drove the prefill, and the auto-pick can land in exactly the "is conflicted"-style dead-end this change exists to kill. The brief's open question 2 explicitly flagged this ("confirm zero-bridge; **translate the one-line bridge if a gap exists**") and the proposal answers only the `?session=` half (zero bridge — verified: `pinnedSessionPayload` hydration at `:3087–3154`). The fallback half is omitted. Fix: specify the fallback's occurrence binding (e.g., client-side `window.pinnedOccurrence = {sessionId: O, week: intentWeek}` before `applySubjectChange`, mirroring the slot-picker rewrite at `:2922–2924` — a real consumer bridge, which also changes the "Blade only" impact claim) — or state that fallback binds module-only and accept the first-session representative with its consequences (that would need a user decision).

**[3] Session-duration × day-end: the new "occupancy" copy can fire with a false cause — falsifying the honesty goal on its own feature.**
Verified facts: The modal filter is type + B005 only (capacity deliberately excluded; duration **not mentioned}). The chosen session's duration reaches the consumer via hydration (`urlParams.duration = pinned.duration`, `:3154`) → `BLOCK_SPAN = hrs*2` clamped 0.5–4h (`:3159–3164`) → `canPlaceBlock` (`:1534–1540`) fails when `startHour + span > hours.length` **or** a cell is held. The consumer's `canPlaceBlock` conflates both causes, and the new copy branch 2 blames *"…(a block already holds it)"*. Today the U2a producer's `BOOK_SPAN = 4` no-fit guard makes the day-end case unreachable via venue handoffs (tooltip toast guard, verified `:228–230`); but from the modal a >2h session (span 6–8) on a ≥2h-but-<3h beehive remainder newly produces the day-end failure — and branch 2 will name the wrong cause, i.e., the change ships a fresh "truthful in effect, imprecise in cause" message in the exact copy set it rewrites to be precise (contradicts Success criterion 4). Fix: a decision one of — (a) modal-side duration-fit check (the payload carries `duration` per scope item 2; the venue page has `hours.length` — disable/exclude [Arrange] for non-fitting sessions, or re-word the message), and/or (b) a fourth consumer copy branch distinguishing "your class duration doesn't fit before day-end" from "a block holds it". Must be resolved in proposal/design before apply.

**[4] Brief open-question 3 (occurrence-label wording) is earmarked "wording at propose" and is absent from the proposal.**
The brief demands distinguishing labels for duplicate occurrences (e.g., *"AMCS2093 (P) · Thu 14:00"*) "so a duplicate-module pick is distinguishable — wording at propose". The proposal's modal spec (scope item 1) settles dropdown contents and ordering but never the label format. Two compatible `P` occurrences of one module would render identical dropdown entries. This is user-visible copy — under house rules a recorded user decision — and the brief explicitly deferred it *to this artifact*. Decide the label format (with honest clues: day/time per occurrence; note the payload also carries `venue`) before freeze.

### 🟡 Should Fix

- **URL contract delta 7-param (brief) → 8-param (proposal, `&week={1-based}`)**: the brief's user-frozen URL template has no `week`; the proposal labels its 8-param version "user-frozen verbatim". `week` is technically **required** (verified: `pinnedSessionPayload` returns null without it, `:128–130`), so the proposal is right and the brief under-recorded the grilling — but the discrepancy must be named: reconcile the brief (declarative append of `week` + rationale) so downstream artifacts don't read the baseline as 7-param.
- **`week` semantics not documented as a consequential decision**: producer passes the venue cell's `currentWeek`; the pinned contract's `week` is the **replaced occurrence's week** in the D1 pair (`submitBlocks` `$requestWeek = $occurrenceWeek ?? $week`, verified `ReplacementArrangement.php:~464–477`). When the user does **not** pick a replacement slot from the picker, the request will "replace" occurrence `(sessionId, venueCellWeek)` — usually the natural default, but if the real conflict lives in another week, picking a slot overwrites the pin (verified `:2922–2924`). The proposal should state this default semantics + the overwrite rule so the design doesn't "fix" it wrongly and the user-decision trail is honest. Beware also the 0-based `currentWeek` → 1-based `week` conversion at design time.
- **Room-type vocabulary mismatch, Lab vs CiscoLab**: `ReplacementArrangement::venuesPayload` maps `cisco_lab → 'Lab'` (consumer filter vocabulary, verified `:160–170`); `VenueTimetable` maps `cisco_lab → 'CiscoLab'` (verified `VenueTimetable.php:63–69`); `mock-data.js:161` uses `'CiscoLab'` + `allowedSessions: ['P']`. The proposal says the modal mapping is "same as the consumer's `venueEligible` matrix" — that is only true after normalization. Design must fix the canonical key (room_type, with `Lab` ∪ `CiscoLab` admissible for P), otherwise the modal filter silently excludes B006 (or everything, if keyed on the wrong vocab).
- **Attribution-note placement unspecified**: scope item 4 says the auto-pick runs through the existing machinery "amber pre-select, pulse, toast" and "an attribution note names the auto-pick" — but the note's host (replace the existing success toast? append to the banner? new toast?) is not decided. Two implementers will diverge, and it is user-visible copy.
