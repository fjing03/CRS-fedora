### 🔴 Critical Issues (implementation blockers)

1. **Fallback path (D3) has no span sizing and runs after a sticky `intentNeedsManual` — recreates the exact round-1 🔴3 false "day-end" cause on the B-path.**
   The modal path sizes the block correctly only because `pinnedSessionPayload` hydration sets `urlParams.duration` → `BLOCK_SPAN` (view :3176–3189, before `applyUrlParams`, :3245). The fallback sets `pinnedOccurrence` + binds the subject (D3 step 2) but **never hydrates duration/span** — so `BLOCK_SPAN` stays the default 4. Two concrete failures, both traced to source:
   - `evaluateBookingFit()` runs **inside** `applyUrlParams` (:3245 → :2608 order: `resolveBookingIntent` → … → `evaluateBookingFit`), i.e. *before* "the end of applySubjectChange-independent boot" where D3 places the fallback. It sets `intentNeedsManual = !canPlaceBlock(i.dayIndex, i.hourIndex)` with the unsized span; `consumeBookingIntent` then short-circuits on the sticky flag (`if (intentNeedsManual || !canPlaceBlock...)`, :2669) and never auto-selects.
   - Worse, if the matched session is *short* (e.g. 1 h = 2 slots) and the booked slot is late such that `hour + 4 > hours.length` but `hour + 2 <= hours.length`, the banner fires the new **day-end branch — "Your class runs longer than the time left before the day end" — about a class that is shorter than the time left.** That is precisely the false-cause defect this change exists to retire, resurrected on the fallback path; and when the flow does complete, the preselected block is default-span (4 slots) instead of session-accurate — breaking the "same duration-fit check … 🔴3 symmetric" equality with the modal path.
   **Fix:** D3 must specify that the fallback writes the matched session's duration into `urlParams.duration` (mirroring the hydration branch, same 0.5–4 clamp family) **before** `consumeBookingIntent`/`evaluateBookingFit` consumes the intent, and reconcile the boot ordering (fallback pre-runs the bind before `evaluateBookingFit`, or `evaluateBookingFit` re-runs after span sizing, with the stale `intentNeedsManual` reset). D3 currently contains none of this.

2. **D1 is self-contradictory about the `sessions` shape, and the contradiction silently breaks the consumer's pinned-session bind.**
   D1 pins "**`sessions` is an ARRAY ordered `(day_of_week, start_time, id)`**" **and** "`coursesPayload()` delegates to `payloadFor(..., null)` … its public return shape stays identical so the arrangement blade's existing consumers are untouched." These cannot both hold: today `coursesPayload` emits `sessions` via `mapWithKeys((string) $s->id …)` — an **id-keyed map** (ReplacementArrangement.php:196ff) — and the blade indexes it **by session id** in exactly two load-bearing places: `courseCtx()` (`currentCourse.sessions[String(currentSessionId)]`, :2341–2342) and the wanted-session bind (`currentCourse.sessions[wanted]`, `Object.keys(currentCourse.sessions)[0]`, :2700–2702). If an implementer ships the sequential array, `sessions[wanted]` is `undefined` → the pinned/fallback session silently falls back to key "0" → `currentSessionId = 0` → `courseCtx` returns module defaults — the same wrong-occurrence failure class the whole pin bridge exists to prevent. Blade edits here are out of impact scope (fallback hook + copy set only). **Fix:** decide the shape once — either the service emits a list **and** `coursesPayload` re-keys it into the id-map (preserving "identical shape"), or the service emits the id-keyed map plus a separate `order` array — and state which; show the shape is preserved at :2341/:2700.
