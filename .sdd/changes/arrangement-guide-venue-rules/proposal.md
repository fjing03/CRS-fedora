# Explain the selected room in the Replacement Arrangement guide

## Purpose and scope

Add **Venue rules** to the existing **How to use this page** modal on Replacement Arrangement. Explain why the current room can or cannot host the exact class occurrence being replaced. Keep the explanation read-only and on this page: no second picker or lookup for filtered-out rooms, no room-wide module roster, no change to role access, server validation, picker results, saved selection, requests, or the database. PLs and ordinary lecturers get the same explanation for their own selected occurrence. Venue Timetable’s room-wide guide is unchanged.

## Domain decisions and copy

- **Default session type**, **module exception**, and **room-wide restriction** keep the definitions in `CONTEXT.md`. The room’s default list is from `LectureSessionCatalog::ruleMap()`, not inventory CSV. For the selected occurrence, show whether its Practical, Lecture or Tutorial is permitted **by default**, permitted **by a module exception**, or **not permitted**. Default takes precedence when both allow arms match. A permissive type row does not override a room-wide restriction.
- **Programme restriction** is a separate check whenever the selected room has one. Show the effective programme list (allowed minus banned; exclusions win). For a confirmed occurrence, explain whether *all* its cohorts meet that rule, whether at least one does not, or whether it could not be checked. Use the same parser and programme checks as the picker, but distinguish explanation states without changing the boolean or its short circuits. A known banned or non-allowed cohort takes precedence over an unknown label, regardless of order; otherwise missing, empty, or unparseable cohort data yields “Could not check”; only a nonempty, fully checked set yields “All cohorts meet the rule.” Evaluate these display facts even if the type is denied. Distinguish a valid empty effective programme list (no programmes listed as allowed) from missing or invalid rule data (restriction could not be checked). The picker’s empty-cohort pass and array fallbacks are unchanged. Do not list other lecturers’ classes or unrelated module exceptions.
- **Capacity** is separate: show seats and the exact occurrence’s student count, e.g. *30 seats for 24 students*, with whether the seats fit. Equality fits. A missing/invalid capacity or headcount is not a pass; show the fact that is known and say the comparison is unavailable. These facts do not mean the room/time is free, that the lecturer and cohorts are free, or that the request can be submitted. No overall green “bookable” verdict.
- Before an occurrence is selected or validly pinned, show only the current room’s defaults, applicable general programme rule and seat capacity. Prompt to choose an original slot for a class-specific explanation. A module selection alone or `courseCtx()`’s representative fallback is not enough. If the current room cannot be resolved, show a neutral no-room state; never manufacture room data from an initial placeholder. Missing rule data does not become “allowed.” A denied state may be explained if the currently displayed room is incompatible; do not make it newly selectable or advertise a diagnostic lookup.

## Interaction and implementation plan

- Use the shared title, tabs, reading pane, and pinned Close controls. Order: **Getting started · Full reference · Venue rules · Shortcuts**. Help opens on Getting started each time; desktop `?` still opens Shortcuts directly. Venue rules is available on mobile, with the existing Shortcuts breakpoint unchanged. Lead with room code/name, then the selected class (module, exact session type and original occurrence label when available), then short sections for the checks above. Reuse guide typography and tokens; text labels carry verdicts independently of colour.
- Read the settled active room from the page’s existing applied venue state, matched against served venue inventory; never use a pending dropdown value that a confirmation can still cancel, or a saved replacement at another venue. For the original class, prefer `selectedOriginalSlot` if present and verify its module, session and zero-based original week against `extractSlotsForSubject(currentCourse.code)` and the exact entry in `currentCourse.sessions`. An explicit valid pick wins over a disagreeing pin (including the same session in another week); if the pick is stale, show no class verdict rather than silently falling back. With no pick, validate `window.pinnedOccurrence` (one-based week; subtract one for the slot rows) against the current module’s rows and session entry, or accept an exact code/session/week match to the ownership-checked `PAGE_DATA.pinnedSession` for the handoff. A pin not backed by either source in the current module is stale. `currentSessionId` alone never proves an occurrence. Read the same occurrence facts the picker uses (type, cohort labels, headcount). Rebuild the panel from live state when the guide is opened, not just from the initial page payload. Changes to class/room become visible on the next open; changing the target week alone does not alter the rule checks.
- Use the existing arrangement client rule evaluation over the canonical server `ruleMap`. Share one set of predicates with the current `venueMatrixAllows()` boolean: expose the underlying default/module/programme results for explanation while preserving the boolean verdict, its fail-closed and empty-cohort semantics, and the `venueEligible()` capacity filter. Do not add a second rule map or a request endpoint. Treat incomplete display data as unavailable, even where a legacy picker fallback is more permissive. Render dynamic labels as text. Do not call booking, selection, revert, or reset functions from the guide.
