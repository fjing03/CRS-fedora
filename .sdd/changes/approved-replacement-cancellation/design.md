# Design — approved replacement cancellation

Baseline: proposal PASS Round 1, frozen 2026-11-14. No new schema or rendering statuses.

## D1. Explicit targets at the shared Livewire boundary
Extend `cancelClass(sessionId, weekNumber, reason, detail, requestId = null, dayIndex = null)` compatibly. For an Approved event the client passes its request ID, landing week and day. Resolve that exact owned Approved request for the active semester and shown coordinate, and verify its source session matches sessionId. Never infer a replacement from sessionId or silently fall back to normal cancellation.

Extend `cancelClassDay(week, day, reason, detail, pendingRequestIds, sessionIds, approvedRequestIds = [])`. The opened replacement contributes ONLY to approvedRequestIds, not sessionIds. Normal recurring selection remains sessionId + shown/source week. Pending withdrawal selection remains request ID. Approved notes in the optional scope remain notes, not ticks. In request-only/approved-only calls empty sessionIds means NO normal classes, not whole-day default. Keep the old both-lists-empty whole-day behavior for legacy callers.

Resolve all submitted normal IDs against dayClasses; unique ID cardinality must equal the selected set, otherwise refuse the entire selection. Resolve approved IDs by actor/source ownership, active semester, Approved state and anchor landing week/day. Refuse overlaps/duplicate target identities rather than closing the same request twice, except harmless repeated IDs within a list are normalized. Return no success when nothing resolves. Re-read targets under locks through D2; pre-lock resolution is not authority. Validate reason/Other detail even if no recurring class is selected. Existing pending withdrawal policy remains unchanged.

## D2. One batch and one lock/release law
Extend CancelClassBatch with an optional approved-target list (`request_id`, `week`, `day`; week/day are LANDING coordinates), accepting an approved-only batch. Keep recurring items unchanged. Both single and day routes call it; the day outer transaction additionally encloses pending withdrawals as today.

Before mutations, lock the complete union with OccurrenceMutationLocks: recurring source items plus all approved and pending request IDs. For approved-only targets use extra request IDs, not recurring items: do not plan or release their original reservations. The helper already advisory-locks extra requests' source sessions then source rows, request union and full landing slot union. Nested calls reuse these held locks.

Preflight AND under-lock validation for approved targets: authenticated lecturer owns both request and source session; source/request/landing belong to active semester; request still Approved; landing week/day match the submitted coordinate; source week valid; full claim is proven by OriginalOccurrenceReservation (junction receipt or existing mapper fallback). Use actual landing date for semester/window/holiday/Sunday gates. The NEW approved-target path always enforces the window on the server, including single cancellation; preserve the legacy normal single-class enforceWindow:false behavior only for recurring targets. Reuse the batch's existing date/window/holiday helpers, not a second calendar. Factor or parameterize only the duplicate-exception check so original cancellation does not refuse approved cancellation. Prepare every normal and approved target before any write. Approved and normal target unions cannot refer to the same active request twice.

Within the same transaction: ReleaseRequestSlots(... attachedLanding: true) while request is Approved; preserve its strict full-claim/newer-holder/OCC behavior. Snapshot actual span/release facts before links disappear, then set request status Cancelled and decided_at. Retain replacement_span, approver/approval evidence and original exception/reason. Do not create/update an original exception and do not release original cells for approved targets. Keep normal batch semantics unchanged.

A refused nested batch stops withdrawals. Any post-write failure throws through the outer transaction and rolls back all classes, requests, links, slots, versions and audits. Notifications register only for successful work and after the outermost commit; best-effort notification failures must not falsely report a rolled-back cancellation.

## D3. Receipts, audits and notification identity
Every `cancelled` receipt contains existing `session_id`, `week` (SOURCE week), `exception_id` when applicable, optional `request_id` for an explicitly cancelled replacement, and server display fields `start`, `end`, `code`, `type`, `venue`, `cohorts`; include actual landing week/day separately for replacement receipts. Normal receipts also gain display fields. Facts come from models/validated mapper span, never posted display strings. requestsClosed includes actual request closures; requestsWithdrawn retains pending-withdrawal meaning.

Approved cancellation writes a legal `cancelled` audit linked to the exact request/anchor, old_status Approved, with reason, optional trimmed Other detail, source session/week, landing semester/week/day/room/full range, links and released-cell before/after evidence. It must NOT fabricate a `class_cancelled` source-occurrence audit: source cancellation is historical and its reason must not change. Existing normal audits remain unchanged.

Notify via the shared NotificationEmitter after outer commit, using an unsaved schedule projection of the original session carrying the actual landing day/time/room and landing week. Never persist the projection. Add an optional request-ID parameter to classCancelled for these request-linked cancellation records; preserve existing request-linked inactive policy without modifying NavNotifications. NotificationTip must use its already-loaded request span and venue for a request-linked Cancelled Class Schedule, not reconstruct the original recurring schedule. Do not reuse the original exception's private reason as the new landing cancellation reason; omit that missing tooltip fact (new reason remains in the cancellation audit). Normal request-less cancellation tips remain unchanged. This preserves actor/cohort/student fan-out and queued delivery. Tests must assert actual body/tooltip landing schedule (including legacy fallback span), no student private reason and no fan-out on refusal/rollback.

## D4. Shared client flow and truthful success
In ui-common.js distinguish an Approved event (`status === replacement`) from a recurring event. Require its requestId. Pass separate targets per D1; do not send its source session among recurring selections. For `_loadDayScope`, exclude the opened item by actual kind/identity: an opened replacement is not a normal day row; remove only its own request from make-up notes, not another week of the same session. Guard against stale async scope results from an earlier modal open.

After server success, Approved cancellation must NOT call ClassCancellation.cancel, append a conflicted MockData row, or create a recurring ledger entry for the landing week. Set the modal's success entry using the server receipt's SOURCE session/week so Arrange Now navigates to the right occurrence. Set an entry for day success as well so Escape/header/overlay dismissal refreshes just like Close. Retain existing normal single-class ledger behavior.

Render `_renderDaySuccess` solely from `res.cancelled` receipt facts: number = array length; list = those rows, with the opened target ordered first only if it is actually in the receipt. Do not synthesize missing primary rows, infer completion from ticks or reuse unsaved schedule facts. Existing count captions/formatting stay intact. A day batch refuses if any requested target is stale; a defensive partial-receipt UI test still must show only acknowledged rows. Single Approved success summarizes its receipt, while keeping Arrange Now/Later. Failures do not flip state or create ledger entries; existing inline error/retry behavior remains.

## D5. Existing projection, not a new history system
No production timeline/ReplacementHome change is expected. Prove that Cancelled request state naturally removes active landing blocks from all four timetables and restores source cancellation under own-Approved suppression. My Replacements retains one SOURCE occurrence row and request ID, shows Need to Arrange, requested slot blank and no Proposed tab. Student projection is Awaiting Arrangement and never exposes private reasons. Preserve original exception/reason/audit and other source weeks/owners. Do not paint a second red historical landing or introduce Cancelled filter/badge changes.

## D6. Test and preservation plan

Check all receipt facts and releases once; released cells reusable and unrelated holdings intact. Add projection assertions for all four timetables and owner/student history using real isolated cancellation.

Read-only Playwright regression: actual shared modal on live pages or browser fixture, intercepted mutation responses (never let mutations through), assert request arguments, single/mixed success, saved-only count/list, failure/no-ledger, dismissal refresh, source-week Arrange Now, responsive/light/dark output. Label interception honestly; backend tests prove persistence. Existing writing browser suite is collected/updated only if needed, never run on protected manual data.
